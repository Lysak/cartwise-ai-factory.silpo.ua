# User Identity and Silpo Connection Design

## Status

Approved Phase 1 design. This document is the implementation authority for Telegram identity, local sessions, Silpo OAuth ownership, and token refresh. The companion decision record explains the review rationale.

## Goal and scope

Cartwise is a production Telegram Mini App with one canonical local identity per verified Telegram user. A local User is created only after successful Silpo OAuth. Silpo OAuth authorizes server-side access to Silpo; Telegram proves the Mini App context.

This phase does not implement ordinary web/desktop login, product catalogue, score, price tracking, promotions, notifications, MCP writes, account merging, or multiple Silpo connections per user.

## Data model

```text
users
- id UUID v7, generated by PostgreSQL 18 `uuidv7()`, canonical Cartwise identity
- telegram_user_id nullable, unique, canonical decimal string
- telegram_username nullable
- telegram_first_name nullable
- telegram_last_name nullable
- telegram_language_code nullable
- created_at
- updated_at

silpo_connections
- id UUID v7
- user_id required, unique foreign key to users.id
- access_token_encrypted
- refresh_token_encrypted nullable
- access_token_expires_at nullable
- refresh_token_expires_at nullable
- status: active | reauth_required
- created_at
- updated_at

oauth_clients
- id UUID v7
- client_id unique
- client_secret_encrypted nullable
- redirect_uri unique
- created_at
- updated_at

oauth_states
- id UUID v7
- state_hash unique
- verifier_encrypted
- redirect_uri
- owner_user_id nullable
- initiating_session_hash nullable
- telegram_user_id nullable
- telegram_username nullable
- telegram_first_name nullable
- telegram_last_name nullable
- telegram_language_code nullable
- expires_at
- created_at
```

`oauth_states` has a PostgreSQL check constraint: exactly one owner form exists.

- First authorization: `telegram_user_id` exists and `owner_user_id` / `initiating_session_hash` are null.
- Reauthorization: `owner_user_id` and `initiating_session_hash` exist; Telegram snapshot fields are null.

`silpo_connections` has an index on `(status, access_token_expires_at)`. `oauth_states` has an index on `expires_at` for cleanup. Redis sessions have no Prisma model.

All UUID primary keys use PostgreSQL 18 `uuidv7()` through Prisma `@default(dbgenerated("uuidv7()"))`; raw SQL uses the same database function.

## Legacy bootstrap cutover

Current unowned `SilpoConnection` rows are OAuth-bootstrap artifacts, not user accounts. Cartwise never assigns them a User from a token, Silpo response, username, or display field.

- A fresh production database starts with the identity-aware schema.
- An environment containing unowned credentials requires an explicit operator-approved cutover. Users re-enter through Telegram and complete Silpo OAuth; only the new owned connection is usable.
- Retirement, deletion, or remote revocation of the old credentials is a separate operator-approved action. No migration performs it automatically.
- A database with unowned credentials must not apply the required `silpo_connections.user_id` migration until this cutover has been approved.

## Telegram bootstrap

The Mini App calls `POST /api/auth/telegram/bootstrap` with the unmodified raw `Telegram.WebApp.initData` in its body. It is never sent in a URL, response, log, or database column.

The backend:

1. Requires the configured same production origin and limits the raw body size.
2. Parses the query string strictly: rejects duplicate keys, missing/invalid `hash`, malformed `user`, and invalid `auth_date`.
3. Builds Telegram's data-check string from all fields except `hash`, sorted lexicographically; verifies the HMAC in constant time with the bot token-derived key.
4. Requires `auth_date` no older than five minutes and no more than 30 seconds in the future.
5. Applies a source-IP limit before validation and a verified Telegram-user-ID limit after validation. The application trusts only the known reverse proxy for forwarded client IPs.

Then the endpoint follows exactly one path:

| Condition | Result |
| --- | --- |
| Valid session with same verified Telegram ID | Renew that Redis session, subject to its absolute expiry. No PostgreSQL lookup. |
| Valid session with different Telegram ID | Delete the old session, then continue below. |
| No valid session; a User exists for verified Telegram ID | Create a rotated local session. OAuth is not repeated solely because a session expired. |
| No valid session; no User exists | Create PKCE and a first-authorization OAuth state containing the verified Telegram snapshot. Return an authorization URL. |

Only the last case may lead to first Silpo OAuth. A verified Telegram username, display name, browser object, or `initDataUnsafe` is never identity evidence.

## OAuth ownership and callback

`POST /api/auth/telegram/bootstrap` creates the OAuth state directly. Production has no ownerless `GET /api/auth/silpo/start` flow.

- State is random, at least 256 bits, held by the browser only as an authorization parameter, and stored as a SHA-256 hash.
- PKCE uses S256. Its verifier is encrypted server-side.
- State expires after ten minutes and is atomically consumed and deleted before code exchange.
- Expired states are periodically deleted.
- Reauthorization begins only from an authenticated local session and records both its User ID and hash of the initiating session ID.
- Before exchange, a reauthorization callback verifies that its initiating session still exists and belongs to its owner. Logout/session revocation invalidates all states carrying that hash.
- The callback exchanges the code, then in one PostgreSQL transaction creates the User when needed and inserts or updates the owned connection. It never creates a second User for the same Telegram ID.
- Concurrent first-authorizations for the same verified Telegram ID resolve the unique User row inside that transaction and upsert its one connection; they never create duplicate Users.
- It creates a fresh local session only after the database transaction succeeds. If Redis is unavailable, authentication fails closed; no JWT or client-held fallback exists.
- Callback success redirects to the fixed same-origin application path. The callback accepts no return URL.

## Server-side sessions

The browser cookie contains a 256-bit random opaque session ID. Redis uses `session:<sha256(session-id)>` as its key and stores:

```text
userId
telegramUserId
issuedAt
absoluteExpiresAt
csrfSecret
```

- Inactivity lifetime is 30 days. A valid request renews Redis TTL with `EXPIRE` to `min(now + 30 days, absoluteExpiresAt)`.
- Absolute lifetime is `issuedAt + 90 days`; it never slides. At expiry, delete the session and require Telegram bootstrap.
- Logout deletes the Redis key. Rotation deletes the old key before writing a new one. Redis unavailability fails authentication closed.
- Normal authenticated requests query Redis only. Bootstrap may query PostgreSQL to find the existing User by verified Telegram ID.

## Transport, cookie, and CSRF

Production uses one HTTPS origin. A reverse proxy serves the React/Vite build at `/` and proxies `/api` to NestJS. `APP_ORIGIN` is the sole source for the OAuth callback URI and fixed post-callback redirect; a DCR client registration is selected only when its stored `redirect_uri` equals that configured value.

Production session cookie:

```text
Name: __Host-cartwise_session
HttpOnly: true
Secure: true
SameSite: Lax
Path: /
Domain: absent
Max-Age: no longer than current Redis TTL
```

Login, reauthorization, account mismatch, and other privilege changes rotate session IDs. `POST /api/auth/logout` requires an authenticated session, exact origin, and CSRF token; it clears the cookie with matching scope attributes and deletes associated OAuth state.

Every future unsafe cookie-authenticated endpoint requires:

1. Exact production `Origin` validation.
2. A CSRF token in a custom request header, verified against the per-session Redis secret.

The OAuth callback is exempt because state and PKCE protect it. Production does not enable CORS. Local Vite proxy development uses a separately explicit insecure HTTP cookie mode; it never changes production cookie attributes.

## Silpo lifecycle

Local session lifetime and Silpo token lifetime are independent.

- One central service resolves a connection only by the authenticated `userId`.
- A cron runs hourly and finds `active` connections expiring within two hours.
- Refresh work is serialized per connection. A transaction may lock one connection while it refreshes and writes its replacement; it never holds one batch transaction over multiple remote requests.
- On demand, the central service refreshes only the selected connection when expired or within one centrally defined safety window. That window is below the observed Silpo access-token lifetime.
- Refresh atomically writes a new access token and any supplied rotated refresh token. If no new refresh token is returned, the existing encrypted refresh token remains.
- Only confirmed token-endpoint `400` or `401` sets `reauth_required`. Network errors, 429, and 5xx are temporary failures.
- An otherwise valid rejected MCP call may refresh and retry exactly once only if its call site explicitly marks the operation read-only. A write is never automatically retried.
- `reauth_required` leaves the Cartwise session valid. API status exposes `SILPO_REAUTH_REQUIRED`, so the UI shows reconnect guidance rather than logging the user out.

## Frontend and testing constraints

- React uses same-origin cookie requests only; it never stores Silpo tokens, local session IDs, bot tokens, or raw `initData` after bootstrap.
- A Vite `VITE_*` variable is public build-time data. No secret, backend URL requiring credentials, encryption key, database URL, Redis URL, bot token, or OAuth credential uses that prefix.
- NestJS is a modular monolith with a session guard and focused services. Do not add Passport, JWT, an external identity provider, BullMQ, Kafka, or microservices.
- Backend tests remain Jest; frontend tests remain Vitest. Mock OAuth/MCP and fake time; tests never require real Silpo personal data.
